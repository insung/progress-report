# Progress Report

진행 상황 질문의 답은 **표 하나**다. 산문 요약이 아니라 단계·할 일·검증 방법·상태를 한 줄에 하나씩 놓고, 상태는 닫힌 목록에서 고르며 「완료」는 세션 안에서 실제로 확인된 증거로만 준다.

## 범위 정하기

1. **기본 범위는 가장 최근의 큰 요청 하나다.** 큰 요청은 새 산출물을 여는 요청이다 — 기능, 계획, 문서, 조사. 그 뒤에 온 수정·질문·커밋 지시는 같은 범위 안의 후속 작업으로 넣는다. 세션 앞부분의 다른 큰 요청은 표에 넣지 않는다.
2. 사용자가 「이번 세션 전체」, 「전체」, 「처음부터」라고 말하면 세션의 모든 큰 요청을 훑는다. 요청마다 표 묶음을 하나씩, 최근 것부터 놓는다.
3. 사용자가 특정 단계나 주제를 짚으면(「1단계 어디까지 됐어?」) 그 부분만 같은 형식으로 낸다.

## 출력 계약

답은 이 순서로, 이 부품으로 이뤄진다.

1. **첫 줄 — 범위와 한 줄 상태.** 어느 요청을 다루는지와 전체 진척을 한 문장으로. 예: 「범위: HTML 미리보기 코멘트 계획. 17단계 중 완료 1, 진행 중 1, 제외 3.」 사용자가 범위를 바로잡을 수 있게 요청 이름을 그대로 쓴다.
2. **표.** 계획에 단계(phase)가 있으면 단계마다 소제목과 표 하나, 없으면 표 하나.

   | 단계 | 할 일 | 검증 방법 | 상태 |
   |---|---|---|---|
   | 0-1 | 설계 문서를 쓴다 | 사용자 검토·승인 | 검토 중 · 사용자 |
   | 0-2 | 시험용 HTML fixture 3종을 정한다 | fixture 파일이 `packages/core/test/fixtures/` 에 있음 | 진행 중 |
   | 1-1 | 텍스트 노드의 소스 위치를 뽑는 토크나이저를 만든다 | `npx vitest run packages/core/test/html-text-map.test.ts` | 완료 · 6건 통과 |
   | 1-2 | 엔티티를 풀고 공백을 접으며 오프셋 지도를 만든다 | 단위 테스트: `&amp;`, 개행 접힘, 앞뒤 공백 | 미착수 |
   | 1-5 | 파일을 srcdoc iframe 에 넣는 웹뷰를 만든다 | 수동: vsix 설치 후 SEO 문서가 글꼴 포함해 그려지는지 | 막힘 · `vsce package` 네트워크 오류, 2회 재시도 |
   | 2-1 | 기존 스레드를 미리보기에 하이라이트한다 | 정하는 중 | 계획 중 |
   | 3-1 | Obsidian 자체 뷰를 만든다 | 허브 볼트에서 `html-viewer` 와 공존 확인 | 이번 범위에서 제외 · VS Code 먼저 |

   위 표는 일곱 상태를 한 번씩 보인 예다. 실제 답에는 해당하는 상태만 나온다.

   - **단계**: 계획에서 쓰던 번호 그대로. 번호가 없던 작업은 순서대로 붙인다.
   - **할 일**: 한 문장, 동사로 끝낸다. 파일이나 함수 이름은 독자가 찾아가야 할 때만 넣는다.
   - **검증 방법**: 실행할 명령, 통과해야 할 테스트, 또는 사람이 눌러 볼 것을 구체적으로. 세션의 계획 표에 검증 방법이 이미 적혀 있으면 그 문장을 그대로 옮긴다. 「확인」이나 「테스트 통과」 한 마디로 채우지 않는다.
   - **상태**: 아래 목록의 일곱 값 중 하나만 쓴다. 다른 말을 만들지 않는다. 근거나 이유가 필요한 값은 `상태 · 근거` 꼴로 한 구절을 붙인다.
3. **대기 중 결정** — 단계로 적히지 않는 선택(방식·진입점·범위)에 사용자의 답이 필요할 때만. 항목마다 추천안을 함께 적는다.
4. **다음 한 걸음** — 한 줄. 지금 당장 이어질 작업과, 사용자에게서 필요한 것이 있으면 그것.

이 네 부품 밖의 문장은 넣지 않는다. 표가 곧 답이다.

## 상태 값

| 상태 | 뜻 | 붙이는 것 |
|---|---|---|
| 미착수 | 계획에 있고 아직 손대지 않았다 | 없음 |
| 계획 중 | 무엇을 할지 정리하는 중이라 검증 방법이 아직 없다 | 없음 |
| 진행 중 | 코드나 문서를 쓰고 있다. 검증은 아직 돌리지 않았다 | 없음 |
| 검토 중 | 산출물이 나와 사용자나 다른 세션의 검토·승인을 기다린다 | 누구의 검토인지 |
| 막힘 | 외부 요인으로 나아갈 수 없다 | 이유 |
| 완료 | 검증 방법을 실제로 실행해 통과했다 | 근거: 테스트 건수, 명령 출력, diff, 커밋 해시 |
| 이번 범위에서 제외 | 이야기됐지만 이 요청에서는 하지 않기로 했다 | 이유, 또는 어디로 미뤘는지 |

## 상태 칸을 채우는 규칙

- 「완료」는 세션 안에 **그 검증이 실제로 실행된 흔적**이 있을 때만 쓴다. 코드를 썼다는 사실만으로는 「진행 중」이다.
- 검증 방법이 「사용자 확인」인 단계는 산출물이 나온 뒤 「검토 중 · 사용자」로 두고, 사용자가 확인했다고 말한 뒤에 「완료」로 바꾼다.
- 세션에서 하기로 했다가 뺀 것, 다음 단계로 미룬 것은 지우지 않고 「이번 범위에서 제외」 행으로 표에 남긴다. 잊히지 않게 하는 것이 이 행의 목적이다.
- 지나가며 언급만 되고 계획에 오르지 않은 아이디어는 행으로 만들지 않는다.

## 지속 규칙

이 스킬이 한 번 발동하면, 같은 세션에서 뒤에 오는 진행 상황 질문에도 같은 계약으로 답한다. 사용자가 「표 말고」, 「그냥 말로」처럼 형식을 바꾸라고 하면 그때 멈춘다.

## 자주 하는 실수

| 실수 | 대신 이렇게 |
|---|---|
| 세션 전체를 완료·미완료 목록으로 나열한다 | 가장 최근 큰 요청 하나만. 전체는 사용자가 「전체」라고 했을 때만 |
| 표 대신 굵은 소제목과 글머리표로 요약한다 | 표 네 열을 채운다. 글머리표는 「대기 중 결정」에만 |
| 검증 방법 칸을 비우거나 「테스트」 한 단어로 채운다 | 어떤 명령·어떤 테스트·어떤 화면인지 적는다 |
| 상태에 「거의 끝」, `[x]`, ✅ 처럼 목록 밖의 표기를 쓴다 | 일곱 값 중 하나. 정도는 근거 구절로 말한다 |
| 코드를 썼으니 「완료」로 표시한다 | 검증 흔적이 없으면 「진행 중」 |
| 뺀 항목을 표에서 지운다 | 「이번 범위에서 제외 · 이유」 행으로 남긴다 |
| 끝에 「진행해도 될까요?」를 덧붙인다 | 「다음 한 걸음」 한 줄이 그 역할을 한다 |
