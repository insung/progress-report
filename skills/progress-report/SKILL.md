# Progress Report

진행 상황 질문의 답은 **범위·목표 요약 표와 단계별 작업 표**다. 목표는 이번에 달성하려는 결과를, 작업 표는 그 결과에 이르기 위한 단계·할 일·검증 방법·상태를 보여준다. 상태는 닫힌 목록에서 고르며 「완료」는 세션 안에서 실제로 확인된 증거로만 준다.

## 범위 정하기

1. **기본 범위는 가장 최근의 큰 요청 하나다.** 큰 요청은 새 산출물을 여는 요청이다 — 기능, 계획, 문서, 조사. 그 뒤에 온 수정·질문·커밋 지시는 같은 범위 안의 후속 작업으로 넣는다. 세션 앞부분의 다른 큰 요청은 표에 넣지 않는다.
2. 사용자가 「이번 세션 전체」, 「전체」, 「처음부터」라고 말하면 세션의 모든 큰 요청을 훑는다. 요청마다 표 묶음을 하나씩, 최근 것부터 놓는다.
3. 사용자가 특정 단계나 주제를 짚으면(「1단계 어디까지 됐어?」) 그 부분만 같은 형식으로 낸다.
4. **목표는 선택한 범위에서 달성하려는 결과**를 한 문장으로 쓴다. 사용자의 요청과 합의된 변경을 근거로 삼고, 할 일 목록이나 현재 상태를 목표로 바꿔 쓰지 않는다. 목표가 아직 정해지지 않았으면 추측하지 않고 목표 칸에 「정하는 중」이라고 쓴다. 세션 전체를 보고할 때는 큰 요청마다 해당 목표를 따로 적는다.

## 출력 계약

출력 구조는 [보고 템플릿](templates/progress-report.md)을 사용한다. 범위·상태·검증 판단의 정본은 이 파일이다.

답은 다음 순서의 부품으로 이뤄진다.

1. **요약 표 — 범위·목표.** 요청 이름을 그대로 쓰고, 달성하려는 결과를 한 문장으로 적는다. 특정 단계만 보고할 때는 그 단계의 목표를 쓴다.
2. **워크트리 — 선택 항목.** 아래 확인 규칙에 따라 관련 워크트리가 있으면 `프로젝트 | 워크트리 경로 | 브랜치 | 용도` 표를 넣는다. 하나·여러 개 모두 같은 형식이다. 확인된 관련 워크트리가 없으면 이 부품을 생략한다. 조회 실패·접근 제한이면 이 위치에 `워크트리: 미확인 · 이유`를 적는다.
3. **작업 표.** 계획에 단계(phase)가 있으면 단계마다 소제목과 표 하나, 없으면 표 하나. 기본 열은 `단계 | 할 일 | 검증 방법 | 상태`다.
   - **단계**: 계획에서 쓰던 번호 그대로. 번호가 없던 작업은 순서대로 붙인다.
   - **할 일**: 한 문장, 동사로 끝낸다. 파일이나 함수 이름은 독자가 찾아가야 할 때만 넣는다.
   - **검증 방법**: 아래 검증 규칙에 따라 명령이나 사람의 확인 기준을 구체적으로 적는다.
   - **상태**: 아래 일곱 값 중 하나. 근거나 이유가 필요하면 `상태 · 근거` 한 구절을 붙인다.
   - **작업 위치**: 여러 위치의 작업을 한 표에 보고하고 워크트리의 용도만으로 각 행의 위치가 불명확할 때만 마지막 열로 추가한다. 구현·검토 용도만으로 대응이 명확하면 기본 네 열을 유지한다. 확정 정보가 없으면 위치를 추측하지 않고 `미확인`으로 적는다.
4. **대기 중 결정 — 선택 항목.** 단계로 적히지 않는 선택(방식·진입점·범위)에 사용자의 답이 필요할 때만. 항목마다 추천안을 함께 적는다.
5. **다음 작업.** 지금 이어질 작업과 필요한 사용자 입력을 한 줄로 적는다.

이 부품 밖의 문장은 넣지 않는다. 세션 전체를 보고할 때는 요청마다 요약 표·해당 워크트리·작업 표를 반복한다.

## 워크트리 확인

- 해당 프로젝트에서 `git worktree list --porcelain`을 조회하고 출력의 `worktree` 경로와 `branch`를 확인한다. 이미 세션에서 조회한 출력이 있으면 그 근거를 사용할 수 있다. 여러 프로젝트는 각각 확인한다. 확인된 경로를 그대로 쓰며 공유 문서의 예시는 리포 상대 경로나 가상 경로임을 밝힌다.
- 현재 보고 범위의 구현·검증·검토 등 용도가 확인된 별도 작업 워크트리만 넣는다. 다른 요청의 워크트리는 제외한다. 기본 checkout만 있는 경우 기본 checkout 자체를 별도 작업 워크트리로 자동 취급하지 않는다.
- 경로나 브랜치를 이름으로 추정하지 않는다. detached HEAD는 조회 결과에 맞게 `detached HEAD`로 적는다. 용도가 확인되지 않으면 관련 작업 위치로 단정하지 않는다.
- 조회 실패는 부재의 근거가 아니다. `워크트리: 미확인 · 저장소 접근 제한으로 목록 조회 불가`처럼 이유를 적고 경로·브랜치 행을 만들지 않는다. 프로젝트 일부만 조회됐다면 확인된 관련 행과 미확인 프로젝트·이유를 함께 표시한다.
- 조회는 보고 근거 확인이며 워크트리를 생성·삭제하지 않는다.

## 검증 방법과 실행 결과

- 해당 프로젝트의 설정·문서·세션에서 실제로 확인한 명령을 쓴다. 작업에 필요한 lint·typecheck·테스트가 있으면 함께 적되, 존재하지 않는 명령을 만들거나 모든 작업에 일괄 적용하지 않는다.
- 계획 표에 검증 방법이 있으면 확인된 문장을 옮긴다. 명령을 아직 확인하지 못했다면 `프로젝트 검사 명령 확인 예정`처럼 예정임을 밝히고, 검증 방법을 정하는 단계는 `계획 중`으로 둔다.
- 문서·UI·사용자 승인 작업은 누가 어떤 링크·화면·문구·절차를 보고 무엇을 판단해야 하는지 적는다. `확인`이나 `테스트 통과` 한마디로 채우지 않는다.
- 검증 방법 칸은 앞으로 수행할 기준이며 실행 증거가 아니다. 상태 칸의 근거와 다음 작업에서 실제 통과한 검사와 미실행 검사를 구분한다. 정한 검증 중 lint만 통과하고 typecheck·테스트가 미실행이면 `진행 중`이다. 자동 검증이 통과해도 필수 사용자 확인이 남으면 `검토 중 · 사용자`다.
- 진행 보고를 위해 검사를 자동 실행하지 않는다. 실행 흔적 없이 통과 결과를 만들지 않는다.

## 상태 값

| 상태 | 뜻 | 붙이는 것 |
|---|---|---|
| 미착수 | 계획에 있고 아직 손대지 않았다 | 없음 |
| 계획 중 | 무엇을 할지 정리하는 중이라 검증 방법이 아직 없다 | 없음 |
| 진행 중 | 코드나 문서를 쓰고 있다. 검증은 아직 돌리지 않았다 | 없음 |
| 검토 중 | 산출물이 나와 사용자나 다른 세션의 검토·승인을 기다린다 | 누구의 검토인지 |
| 막힘 | 외부 요인으로 나아갈 수 없다 | 이유 |
| 완료 | 검증 방법을 실제로 실행해 통과했다 | 근거: 테스트 건수, 명령 출력, diff, 커밋 해시 |
| 이번 범위에서 제외 | 이야기됐지만 이 요청에서는 하지 않기로 했다 | 이유, 또는 어디로 미뤘는지 |

## 상태 칸을 채우는 규칙

- 「완료」는 세션 안에 **그 검증이 실제로 실행된 흔적**이 있을 때만 쓴다. 코드를 썼다는 사실만으로는 「진행 중」이다.
- 검증 방법이 「사용자 확인」인 단계는 산출물이 나온 뒤 「검토 중 · 사용자」로 두고, 사용자가 확인했다고 말한 뒤에 「완료」로 바꾼다.
- 세션에서 하기로 했다가 뺀 것, 다음 단계로 미룬 것은 지우지 않고 「이번 범위에서 제외」 행으로 표에 남긴다. 잊히지 않게 하는 것이 이 행의 목적이다.
- 지나가며 언급만 되고 계획에 오르지 않은 아이디어는 행으로 만들지 않는다.

## 지속 규칙

이 스킬이 한 번 발동하면, 같은 세션에서 뒤에 오는 진행 상황 질문에도 같은 계약으로 답한다. 사용자가 「표 말고」, 「그냥 말로」처럼 형식을 바꾸라고 하면 그때 멈춘다.

## 자주 하는 실수

| 실수 | 대신 이렇게 |
|---|---|
| 세션 전체를 완료·미완료 목록으로 나열한다 | 가장 최근 큰 요청 하나만. 전체는 사용자가 「전체」라고 했을 때만 |
| 요청 이름이나 할 일만 적고 목표를 생략한다 | 요약 표의 목표 칸에 이번 범위에서 달성하려는 결과를 한 문장으로 적는다 |
| 표 대신 굵은 소제목과 글머리표로 요약한다 | 기본 작업 표 네 열을 채운다. 글머리표는 「대기 중 결정」에만 |
| 검증 방법 칸을 비우거나 「테스트」 한 단어로 채운다 | 어떤 명령·어떤 테스트·어떤 화면인지 적는다 |
| 상태에 「거의 끝」, `[x]`, ✅ 처럼 목록 밖의 표기를 쓴다 | 일곱 값 중 하나. 정도는 근거 구절로 말한다 |
| 코드를 썼으니 「완료」로 표시한다 | 검증 흔적이 없으면 「진행 중」 |
| 뺀 항목을 표에서 지운다 | 「이번 범위에서 제외 · 이유」 행으로 남긴다 |
| 끝에 「진행해도 될까요?」를 덧붙인다 | 「다음 작업」 한 줄이 그 역할을 한다 |
